从0开始学web-02:异步编程

高并发

高并发是指在短时间内有大量请求同时到达服务器的情况，是一个系统或应用程序在同一时间能够处理大量请求的能力 。

衡量高并发系统能力的关键指标：

QPS（每秒查询率）：每秒处理的请求数。
RT（响应时间）：请求从发起到得到响应的耗时。
吞吐量：单位时间内处理的请求数量或数据量。
并发用户数：同时在线并活跃的用户数量 。

常见的比如选课时（破e江南！），抢票，出现热搜微博崩了，就是一瞬间涌入了大量的用户请求。

日常实例分析

我在想为什么微博这么容易崩，抖音不崩呢？抖音之类的短视频平台人那么多，每瞬间点进去的人应该来说要比大家在一个时间段看热搜的人多一些吧，或者说相差不大？为什么从没见过这些短视频平台崩掉呢？还有e江南每次抢课就那么点人，几千人为什么还会崩掉呢？

搜索之后附上解释。

短视频平台（抖音、B站）是“被动投喂”与“流量分散”：抖音采用竖屏无预览的算法推荐模式，用户是被动接收内容的。当海量用户涌入时，系统会把用户分散到无数个不同的视频流中。这意味着，流量被均匀地“摊薄”了，很难形成对某一个单一数据接口的集中冲击。

微博是“主动聚焦”与“热点引爆”：微博的核心引擎是“热搜榜”，它是基于用户的主动搜索、转发和评论来驱动的。一旦某个明星官宣或突发新闻爆发，几千万用户会在同一秒钟去搜索同一个关键词、刷新同一个话题页、点击同一个明星的主页。这种高度集中的流量，在技术上被称为“Redis 热 Key（Hot Key）”问题。

Redis 热 Key（Hot Key）问题，简单来说，就是某个或某些 Key 的访问频率远超其他 Key，导致处理该 Key 的 Redis 节点 CPU 飙升、响应变慢，甚至引发集群中某个分片“过热”而影响整体服务 。

总之，微博之所以容易崩，是因为它的“热搜”机制天然容易制造极端的“热 Key”并发场景，瞬间打穿单点缓存；而短视频平台通过算法将流量分散，避免了这种极端的集中冲击。这并非是因为微博人更多，而是两者产品基因和技术架构决定的。

为什么微博不升级一下自己呢？因为微博的流量特征是“瞬间峰值高、持续时间短”，如果为了应对这短暂的几分钟而盲目配置大量服务器，在非高峰时段会造成极大的资源浪费和成本增加。因此，运营商通常只保留适度的冗余，一旦流量真的失控，就不管了。

为了让电脑同时干多件事发明的几种编程模型

同步编程

单线程。只能等这个任务处理好了再处理下一个，这个任务100秒，下个任务3秒也得按照先后顺序等待。买奶茶去排一队一直等。

异步编程

单线程。这个任务100秒，下个任务3秒，都给你处理，你会在等待100秒任务完成的间隙完成那个3秒的任务。似乎有点像多线程？但其实不是，多线程是同时做这两件事，但是这个就像托管了一件事，然后呢等待期间去完成另一件事了。给你个取餐器，你先去干别的，等餐做好了再回来取。

异步编程

传统的同步编程根本扛不住高并发。因为每次请求都要“死等”网络回复（I/O 阻塞）。而异步编程就是处理高并发的一种重要有效的方式。

在同步编程中，等待 I/O 操作（如网络请求、文件读写）完成时程序会阻塞。而异步编程允许我们在单个线程中同时处理多个任务，无需使用多线程或多进程。

核心优势：极大节省系统资源，特别适合处理大量 I/O 密集型的网络爬虫或并发请求。

协程（Coroutine）

实现异步的 Python 神器
协程是可以在执行中途暂停、之后从暂停处恢复的函数。通过 async def 定义，通过 await 暂停。像是一个带有“存档/读档”功能的函数。普通函数必须一口气跑到 return 才结束，而协程跑到一半，遇到 await 觉得太耗时间了，直接“存档”退出，把控制权交出去。等网速恢复了，再“读档”从刚才那行接着跑，而不是从头再来。

C 语言的“断点” 与 Python 的 await 的区别

我发现 await 和 C 语言的“断点”都是暂停，那区别在哪里呢？

断点（Breakpoint）：是调试工具（Debugger）的功能。你在 IDE 里打个红点，程序运行到那里，整条线程被强行冻结（暂停一切）。这是上帝视角的干预，程序是被动的。

await：是代码逻辑。遇到网络请求，当前协程主动让出 CPU 控制权，告诉事件循环：“我去后台等网速了，你赶紧去跑别的任务，别因为我卡住整个程序”。这是非阻塞的状态。
